# Feature matrix

Which features Mallard combines, and how far each combination is trusted: every
pair of features is marked with the strongest evidence the repository holds for
it, linked to that evidence (hover over a mark for its test, study, case or
guard).

| Mark | Meaning | Evidence |
|---|---|---|
| **val** | Validated for a regime | A case of the [validation page](https://matthewbonanni.github.io/mallard/validation/) uses both, compared with experiment, DNS, theory or another code |
| **ver** | Verified | A convergence study of the [verification manual](../verification/index.md) uses both and converges at its design order |
| **imp** | Implemented | A test of the test suite runs both; for MPI and CUDA, a build of the [support matrix](support.md) runs the whole test suite, which runs the flow solver with that feature |
| **rej** | Rejected | The input check stops with an error: the combination is not supported |
| · | Untested | None of the above: it may work, but nothing checks it (the [test gaps](#untested-combinations)) |
| (empty) | | A run uses one of these at a time (the reconstructions, the Riemann solvers, the time integrators, Euler or Navier-Stokes, the GPU backends) |

A mark on the diagonal (in bold) is the feature's own evidence. The tables count
combinations of two features; a run that combines three is evidence for each of
its pairs.

## How the page is made

[`tools/docs/feature_matrix.py`](../../tools/docs/feature_matrix.py) writes the
tables from the repository's own records, and CI fails when they are out of date
(`python3 tools/docs/feature_matrix.py --check`):

- **rejected**: the input guards in `src/`. The script names each guard by its
  message: those that reject a pair, and those that make a feature need another
  (LES needs Navier-Stokes, so it is rejected with Euler and with whatever
  Navier-Stokes is rejected with). It fails on any guard saying "not supported" or
  "not available" that it does not name;
- **validated**: the `validation` entry of an example's `card.toml` (the section of
  the validation page and the regime it covers), with the features read from the
  example's input file;
- **verified**: the studies of
  [`docs/verification/results.json`](../verification/results.json), with the
  features their tests declare and the method each study names;
- **implemented**: [`test/features.toml`](../../test/features.toml), where each test
  lists the features of its runs; every test of the verification manual must be
  listed. MPI and the GPU backends also take the builds of the
  [support matrix](support.md) that run the full suite.

A new test of a combination adds its line to `test/features.toml`, a new guard of
a pair its entry to the script's `GUARDS` (or `REQUIRES`), and a new validation case its
`validation` entry to the example's `card.toml`; then run the script.
